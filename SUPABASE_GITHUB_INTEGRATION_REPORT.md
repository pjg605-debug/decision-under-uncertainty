# Supabase / GitHub Integration Report

## Outcome

Decision / T0 now has a reproducible shared editorial desk. GitHub holds the implementation contract and fallback content; Supabase holds normalized content and workflow state. The product reads approved remote content without exposing write credentials and falls back to the six bundled cases when the remote reader is unavailable.

## Supabase schema

The migration creates `decision_cases`, `decision_options`, `case_information`, `evidence`, `narratives`, `case_scores`, `reviews`, `revisions`, `shorts_variants`, `publication_results`, `agent_runs`, `status_transitions`, `research_claims`, and `research_gaps`.

- Migration: `supabase/migrations/202608300001_content_hub.sql`
- Seed: `supabase/seed.sql`, generated by `scripts/generate-supabase-seed.mjs`
- Database checks: `supabase/tests/editorial_workflow.sql` and `supabase/tests/rls.sql`

## Security

All fourteen content/workflow tables use RLS. Browser roles receive `SELECT` only on approved case content, current approved narratives, scores, and approved shorts variants. They receive no write grants and no access to reviews, revisions, agent runs, status history, research queues, or publication results.

The browser bundle contains neither `SUPABASE_SERVICE_ROLE_KEY` nor a direct administrative client. The public content route uses only `SUPABASE_ANON_KEY`. The internal review route uses server-only credentials plus a separate dashboard token.

Environment contract:

- `SUPABASE_URL`
- `SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY` — server only
- `REVIEW_DASHBOARD_TOKEN` — server only
- `SITE_URL`

Actual values are excluded by `.gitignore`; `.env.example` contains names only.

## Fixture migration

The seed migrates Austerlitz, Cuban Missile Crisis, Challenger, Netflix Streaming, New Coke, and Apollo 13. Structured facts, T0 information, future information, options, evidence, narrative versions, scores, and shorts variants are stored separately. Existing `data/` JSON and TypeScript fixtures remain intact as fallback.

The Cuban Missile Crisis seed includes an auditable sample loop: Claude narrative v1 → Codex revision review → Claude narrative v2 and `revisions` record → Codex approval. The database workflow test repeats the full state sequence inside a transaction and rolls it back.

## Application connection

`/api/content` reads normalized approved rows through Supabase REST and transforms them back into the existing `DecisionEvent` contract. The client starts with local fixtures, replaces them with remote content after a successful fetch, and retains the current case by case ID. Result hiding, progressive evidence, Compare, Shorts Preview, language selection, and local My Decisions behavior remain unchanged.

`/review` is a separate internal surface showing case status, current narrative version and author, open reviews, severity, research gaps, and approve/revision actions.

## Queue usage

Claude:

1. Run `get-case-for-research` for `DISCOVERED` / `RESEARCHING` cases.
2. Store evidence/research and transition to `RESEARCH_DONE`.
3. Run `get-case-for-narrative`, then `submit-narrative-version` and transition to `NARRATIVE_DRAFTED`.
4. Run `get-revision-requests`, submit a new version with `triggered_by_review_id`, and transition to `REVISION_DONE`.

Codex:

1. Run `get-case-for-codex-review` for `NARRATIVE_DRAFTED`, `REVISION_DONE`, or `CODEX_REVIEW`.
2. Validate schema, evidence references, T0 fairness, display limits, and reveal boundaries.
3. Run `submit-review` with `APPROVE` or `REVISE`; revision requests advance the case to `REVISION_REQUESTED`.
4. Re-review `REVISION_DONE` and advance passing content to `APPROVED`.

## Exact Claude handoff

Use the Supabase project URL from the environment and a server-side service credential. Never place that credential in a browser, narrative file, Git commit, output, or prompt. Run `pnpm editorial get-case-for-narrative 10` to claim a `RESEARCH_DONE` case. Submit prose with `pnpm editorial submit-narrative-version '<json>'`, preserving canonical facts and evidence. For revision work, first run `pnpm editorial get-revision-requests 10`, include `triggered_by_review_id`, create a new version, record a concise change summary, and move the case to `REVISION_DONE`. Do not overwrite a narrative version or alter canonical T0/evidence without a review and audit trail.
